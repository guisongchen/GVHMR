# 提案：用 SAM3 替换人体检测与追踪模块

> 状态：**待验证**（计划单独开分支实验）
> 日期：2026-09-20
> 相关模块：`hmr4d/utils/preproc/tracker.py`（当前实现：YOLOv8x + ByteTrack）
> 背景文档：[`docs/PIPELINE.md`](../PIPELINE.md) 第 2.1 节

## 1. 动机

当前 Tracker 基于 YOLOv8x 检测 + ByteTrack 追踪，策略是"取最长的一条单人轨迹 + 线性插值补缺 + 滑动平均平滑"。在简单单人场景下工作良好，但存在已知短板：

- 遮挡 / 出画再入画后容易丢轨迹或发生 ID switch（"最长轨迹"可能只覆盖半个视频）
- 多人场景无法指定目标，只能被动接受最长轨迹
- 无法利用分割信息

SAM3（Meta, 2025-11）提供 promptable 的开放词汇检测 + 视频实例追踪 + mask 输出，理论上可以覆盖上述短板。

## 2. 误差传导分析：Tracker 的输出到底影响什么

Tracker 的 bbox（`bbx_xyxy` → `bbx_xys`）有四条下游通路，敏感度不同：

| 下游 | 敏感度 | 说明 |
|---|---|---|
| ViTPose 裁剪窗口 | 中 | 窗口偏移/抖动轻微影响 2D 关键点质量 |
| HMR2.0 特征裁剪 | 低 | 1024 维全局特征对裁剪很鲁棒 |
| **`s` → 深度估计 `2f/(tz·s)`** | **高** | 直接决定 `transl` 尺度（`hmr4d/utils/geo/hmr_cam.py:146`） |
| `normalize_kp2d` 归一化 | 低 | 归一化本身消除绝对误差 |

**关键结论**：bbox 最重要的作用是提供尺度 `s`，而非"框住人"。`s` 经过宽高比修正（0.75）+ 1.2 放大 + 滑动平均平滑后已相当钝化，检测框 ±10% 的抖动对最终结果影响很小。

## 3. 预期收益评估

### ✅ 有实质提升的场景

- **遮挡与 ID 切换**：SAM3 视频追踪基于外观记忆，遮挡恢复能力远强于 ByteTrack 的运动关联。对长视频、多人穿插场景是质变。
- **多人场景指定目标**：文本/点提示（"the person in red"）交互式指定目标，比"自动选最长轨迹"灵活，适合可交互预处理工具。
- **mask 副产品**：mask 推出的 bbox 更贴合身体；mask 本身（人体轮廓）可作为额外条件信号（见 §6 研究向扩展）。

### ❌ 提升有限的场景

- **普通单人视频**（demo 场景）：YOLOv8x 在 person 类别已很准，残余误差被平滑/修正吸收，端到端精度大概率几乎不变；3DPW 类 benchmark 预计看不到显著提升。
- **速度**：SAM3 视频追踪比 YOLO 重约一个量级。预处理已占 demo 绝大部分耗时（参考：GVHMR 推理 0.26s / 预处理数分钟），换装会进一步拉长。

## 4. ⚠️ 关键风险：`s` 的分布漂移

**这是最容易翻车的地方。** 深度估计公式 `gt_s = 2f/(tz·s)` 和 GVHMR 网络都是在 **YOLO 风格检测框的尺度分布**上训练的。SAM3 从 mask 推出的是**紧贴身体轮廓的紧框**，同样流程下 `s` 会系统性偏小，导致：

- 估计深度系统性偏远
- `transl` 整体尺度错误

**必须做的对齐**：标定新的 `base_enlarge` 系数（当前 1.2）。方法：用若干视频同时跑 YOLO 框和 SAM3 框，统计 `s` 的比值分布，调整 enlarge（mask 紧框预计需要 1.4~1.6）使分布对齐。不处理这一步，精度不升反降。

## 5. 实验计划（分三步，投入递增）

| 步骤 | 内容 | 工作量 | 验收标准 |
|---|---|---|---|
| **Step 1：无痛替换** | `SAM3Tracker` 只输出 bbox，接口对齐 `Tracker.get_one_track() -> bbx_xyxy (L,4)`；标定 enlarge 系数 | ~半天 | demo 视频结果与 YOLO 版肉眼无差异 |
| **Step 2：压力测试** | 收集 YOLO 失败场景：多人交叉、严重遮挡、出画再入画；对比两条 pipeline 的轨迹完整性与最终结果 | ~1 天 | SAM3 在失败场景轨迹完整，YOLO 版断裂处 SAM3 正确 |
| **Step 3：mask 条件信号**（研究向，可选） | silhouette 作为第 5 路条件输入 `hmr4d/network/gvhmr/relative_transformer.py`，需重训 | 研究项目 | benchmark 指标提升（思路与 RICH 的场景/接触条件类似） |

## 6. 实现备忘

- **改动点**：仅 `hmr4d/utils/preproc/tracker.py`，新增类保持接口兼容即可，不影响 pipeline 其余部分。
- **缓存机制**：预处理结果缓存于 `outputs/demo/<video>/preprocess/bbx.pt`，对比实验时需删除该缓存强制重算。
- **对比工具**：demo 加 `--verbose` 会输出 bbox 叠加视频（`bbx_xyxy_video_overlay.mp4`），可直接肉眼对比两条轨迹质量。
- **本机环境**：已有 `sam_3d_body` conda env 可作参考；注意 gvhmr env 的 torch 版本为 2.3.0+cu121，SAM3 的依赖需确认兼容。
- **分支命名建议**：`feat/sam3-tracker`

## 7. 结论（预登记，待实验检验）

1. demo 场景精度收益微小 —— YOLOv8x 不是瓶颈（瓶颈在 ViTPose 2D 关键点质量与网络本身）；
2. 鲁棒性与场景边界（多人、遮挡、指定目标）值得换 —— 产品化时 Tracker 是最先暴露问题的环节；
3. 换装必须处理 `s` 尺度分布对齐，否则引入系统性深度偏差。
